# 项目内工作区迁移计划

> 状态：第一阶段已落地，后续迁移阶段继续通过独立 `PR`（拉取请求）完成。

## 已落地的第一阶段

- 应用全局索引记录当前项目和最近使用的项目。
- 工具条可以选择项目；项目没有 `.dockyard`（项目设计目录）时，必须确认后才创建。
- 已有项目工作区从项目内读取，保存时写回项目内；组件全局缓存仍保留在应用数据目录。
- 旧全局工作区仍作为兼容回退，待迁移界面完成后再停止写入。

## 文档目标

当前版本把设计工作区保存在 `Dockyard`（应用）的全局应用数据目录中。后续调整为“一个代码项目对应一个设计工作区”，设计记录保存在项目内部；全局应用数据只保留应用配置、最近项目、窗口状态和可复用缓存。

这项调整的目标是让图稿、标注、决策、令牌、组件引用和开发上下文与代码项目一起移动，避免由 `Dockyard`（应用）单独管理一组缺少项目归属的工作区。

## 目标使用方式

1. 启动工具条时读取最近一次有效项目；没有有效项目时先显示项目选择界面。
2. 用户选择代码项目后，读取项目中的 `.dockyard`（项目设计目录）。
3. 项目尚未建立设计工作区时，先显示将创建的目录和内容，再由用户确认创建。
4. 切换项目时保存当前工作区，再加载目标项目的设计数据。
5. 项目被移动或重命名后，用户可以重新定位；应用按工作区标识确认是否为同一个项目。

## 数据边界

项目内部保存与项目设计直接相关、需要随项目移动的数据：

```text
.dockyard/
  workspace.json
  design.json
  artworks/<artwork-id>/scene.excalidraw.json
  assets/source/
  assets/previews/
  assets/components/
  context/
```

全局应用数据只保存机器级或可重新生成的数据：

```text
config/
recent-projects.json
window-state.json
cache/component-catalog/
cache/visual-assets/
logs/
runtime/
```

模型供应商配置及密钥环境变量名称属于全局配置，不能写入项目。组件索引、视觉资源、临时渲染环境和调用日志也不能进入用户项目。

## 项目文件的版本管理

项目内设计记录默认允许由项目自行决定是否提交到版本管理。创建工作区时应提供说明，并生成只排除临时内容的 `.dockyard/.gitignore`（版本管理忽略规则）。原图和预览图可能包含敏感信息或占用较大空间，是否提交必须由项目成员决定，应用不能自动执行版本提交。

项目设计数据使用相对路径引用同一工作区中的资源，不能保存依赖当前机器盘符的绝对路径。写入继续采用临时文件替换，避免保存中断后破坏已有数据。

## 旧工作区迁移

迁移不能在首次启动时静默执行，也不能立即删除原数据。计划采用以下流程：

1. 检测全局应用数据目录中的旧工作区，并列出名称、图稿数量、最近更新时间和占用空间。
2. 用户为旧工作区选择目标代码项目。
3. 迁移前检查目标项目中是否已经存在 `.dockyard`（项目设计目录），存在时提供合并、另存或取消，不直接覆盖。
4. 将工作区复制到目标项目，转换绝对路径并校验图稿、场景和资源数量。
5. 成功后在旧工作区中记录迁移目标和时间，但保留原数据供恢复。
6. 原数据只能由用户通过单独的清理操作移入回收站。

一次迁移失败不能影响其他工作区，也不能改变应用当前选中的有效项目。

## 实施阶段

1. 定义项目工作区版本、目录清单和路径校验规则。
2. 增加项目选择、最近项目和当前项目状态。
3. 将工作区读取、保存和上下文生成改为基于当前项目目录。
4. 把组件缓存、模型配置、日志和运行文件迁出工作区，固定为全局数据。
5. 增加旧工作区迁移界面、冲突处理、校验和恢复记录。
6. 更新使用说明，并覆盖新建、切换、项目移动、只读目录和迁移失败等测试。

## 验收标准

- 没有选定项目时，不创建匿名设计工作区。
- 每个项目只加载自己的 `.dockyard`（项目设计目录），项目之间的数据不会混用。
- 复制或移动整个项目后，设计工作区仍能正常读取。
- 组件缓存、视觉资源、模型配置和日志不会写入项目目录。
- 旧工作区迁移前有明确预览和确认，失败时原数据保持可用。
- 目标目录已有数据时不会被静默覆盖。
- 保存失败会显示具体位置和原因，不会破坏上一份有效数据。
