Dockyard 内部架构

从上到下是调用方向；每一层只与相邻层交互。

应用界面桌面协调本地服务持久化资料
01 · 界面层
工作条Dockyard 的入口与窗口切换
＋
图稿 · 检索 · Token · 决策React 视图：显示数据，接收操作
02 · 应用桥接层
preload（安全桥接）将允许的 window.dockyard（前端桥接对象）能力交给界面层
03 · 桌面协调层
Electron main（主进程）窗口管理 · 文件保存 · 组件检索 · 生成开发上下文
→
临时 MCP 服务设计状态 · 预览 · 已确认组件 · 设计备注
04 · 设计服务层
评审桥接接收评审 HTML 的逐项决定
→
Dockyard MCP读取设计上下文 · 校验评审 · 写入决定记录
→
codex（命令行代理）仅用于组件候选检索
05 · 数据层
design/（设计资料）规则 · Token · 评审 · 决定 · 范围化记忆
＋
.dockyard/context/（项目上下文包）输出至用户选定的开发项目

设计状态如何流转

上面是模块分层；下面只说明一项设计建议从产生到确认的状态变化。

① 候选

组件检索或设计分析产生候选项；还没有改变项目设计。

仅在界面内
→
② 待评审

生成评审 HTML，包含建议、证据和关联 Token。

design/reviews/
→
③ 用户决定

逐项选择“接受、拒绝或讨论”，可以留下评论。

design/decisions/
→
④ 已确认

只有“接受”会成为项目设计基线，供后续上下文读取。

Token / context-memory
拒绝 / 讨论

保留决定和评论；不更新 Token。讨论后的新信息会写入范围化记忆，避免在相同条件下重复询问。

↗
下一轮上下文

MCP 只读取与当前界面、组件和条件相匹配的已确认结论或讨论记录。

长期记忆的边界：范围化记忆属于数据层，由 MCP 按“界面 / 组件 / 条件”筛选后进入下一轮上下文；它不会作为全局规则直接影响所有页面。

评审路径：评审 HTML → 本机评审桥接 → Dockyard MCP → design/decisions/（逐项决定记录）。只有接受的关联项才会更新 Token。
